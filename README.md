## 扫雷两个阶段：怎么实现、怎么验证
### 阶段一：先做出"能自己玩"的版本
**怎么实现的**
整个游戏是一个 HTML 文件，里面的 JavaScript 分成两块：
1. **引擎**：纯逻辑，只管棋盘数据（哪格是雷、有没有翻开、周围几颗雷、赢还是输），完全不碰网页元素（DOM）。
2. **界面**：只负责把引擎的数据画到屏幕上，以及把鼠标/触屏操作翻译成引擎能懂的调用。
这样分层的原因见下面"阶段二"——引擎不依赖界面，就可以被单独抽出来做批量测试。
界面的经典扫雷观感是用 CSS 的立体边框做出来的：未翻开的格子用"左上亮、右下暗"的边框，看起来是凸起的按钮；已翻开的格子去掉立体感、只留一条浅色分隔线；顶部的计数器和笑脸按钮则反过来用"左上暗、右下亮"，看起来是凹进去的。数字 1–8 也是按经典配色（1 蓝、2 绿、3 红……）。
**怎么验证的**（ai自己验证自己跑的）
1. **静态检查**（`node tools/check-game.js`）：把文件里的 JavaScript 交给 Node.js 做语法编译检查（只看能不能通过语法解析，不执行），再检查 HTML 标签是否成对、界面代码引用的 23 个元素 id 是否都真实存在、任务书要求的功能关键词是否齐全——全部通过。
2. **界面层测试**（`node tools/test-ui.js`）：这一层是补上的。它用一个极简的假 DOM 把整个游戏跑起来，然后**真的去"点"格子**，检查数据变化之后界面有没有跟着更新。目前 19 项断言全部通过，覆盖"点数字展开周围"、"切换角色主题并存进本地"、"列出该角色的卡面"、"通关后所有雷都被标出来"、"战绩只保留最近 10 局"、"AI 打完一局不会自动停"等。
3. **卡面地址校验**（`node tools/verify-cards.js 40`）：内置卡面是按"资源编号"拼地址的，编号错一位就会变成碎图。脚本会逐个请求并检查**文件头是不是 PNG**（那个站点对不存在的路径也返回 200，只查状态码没有意义）。抽查 40 位角色各一张：**40/40 成功**，图片大小 422KB–837KB。
4. **手动试玩**（这一步必须在浏览器里做，代码检查代替不了画面）：左键翻开、右键插旗、点数字快速展开、故意踩雷看失败表现、赢一局看是否出现 😎 并自动标出所有雷、切主题后按 F5 刷新看是否保留、点「重置统计」看是否归零、把窗口缩小到手机宽度看布局有没有溢出。
### 阶段二：让 AI 来玩（自动演示）
**硬指标**：AI 自动完成标准局（9×9、10 雷），翻开全部安全格且不踩雷，随机雷区下连续通关 2 局，全程无需人工操作。
**怎么实现的**
AI 的决策分三层，从"确定"到"猜"，只有前两层推不出来才会用第三层：
1. **基础规则（必然结论）**：每个已翻开的数字都表示"我周围这些没翻开的格子里，恰好有这么多颗雷"。如果这个数字周围的雷已经全部被插旗，那么剩下的未知格**一定安全**，直接翻开；反过来，如果未知格的数量正好等于剩余雷数，那这些格子**一定是雷**，直接插旗。
2. **子集规则（推理）**：如果数字 A 周围的未知格完全包含在数字 B 的未知格里，那么"B 比 A 多出来的那些格子"里的雷数就等于 `B 的数字 - A 的数字`。这个差值常常是 0 或者等于格子数，于是又能推出新的必然安全格或必然雷格。
3. **概率计算（猜，但猜得聪明）**：前两层都推不动时，AI 会把边界上所有未知格按"互相有联系的"分成若干组，**穷举出每一组里所有符合约束的布雷方式**，再结合"全盘还剩几颗雷"这个总条件，算出每一格是雷的准确概率，然后挑概率最低的那格翻开；如果棋盘上还有完全没线索的区域，会算出那里的平均雷概率一起比较，通常优先去开新区域——因为开一片新区域能带来大量新线索。
另外，开局没有任何线索时，AI 优先点**角**，其次是**边**——因为角上相邻格最少，猜错的代价最低。
**连胜怎么算**：AI 每赢一局连胜 +1，踩一次雷连胜归零，「最长连胜」记录历史最好成绩；按停按钮再继续**不算中断**（只有真的踩雷才算），所以放着让它跑也能累积出很高的连胜数。
**怎么验证的**
我没有用"看它跑几局好像都赢了"这种主观判断，而是写了 [tools/simulate-minesweeper.js](tools/simulate-minesweeper.js)：它把 `minesweeper.html` 里的引擎代码抽出来，用完全相同的 AI 逻辑反复随机开新局，然后统计结果。运行方式：

```bash
node tools/simulate-minesweeper.js 2000
```

实测结果（标准局 9×9、10 雷）：
| 指标 | 结果 |
|---|---|
| 总胜率 | **95.8%**（1915 / 2000） |
| 最长连胜 | **72 局** |
| 首次达成"连续通关 2 局" | 第 2 局 |
| 平均每局操作数 | 29.2 次 |
| 异常卡死局数 | 0 |
| 2000 局总耗时 | 0.5 秒 |
另外还跑了 200 次"从零开始打到连续通关 2 局"的独立测试，**200/200 全部成功，平均 2.10 局、最多 4 局就能达标**。这说明任务书要求的"随机雷区下连续通关 2 局"是稳定可达成的，而不是碰运气

## 进阶挑战：复现 Croc 开源芯片项目

## 踩过的坑

1. **GitHub 的 HTTPS 端口被网络阻断，`git push` 一直超时。**
   报错是 `Failed to connect to github.com:443 after 21040 ms`。逐个测试后发现：`github.com:443` 不通，但 `github.com:22`（SSH）和本机代理端口是通的。最后让 Git 走本机代理（`git config --global http.proxy`）才推上去。
   本质其实应该是校园网的问题，有时候上不去挂一下梯子又可以提交了

3. **邮箱链接点开是空白页。**
   网页里的 `mailto:` 写法本身没错，它的作用是"调用系统的默认邮件程序"。后面才发现我电脑因为没有下这种软件所以浏览器无处可去，只能开一个空白标签页。解决办法是保留 `mailto:`（访客装了邮件客户端就能正常用），另外加一个「复制」按钮兜底。

4. **`git status` 里中文文件名显示成 `"\345\244\247..."` 这样的乱码。**
   这是 Git 对非 ASCII 文件名的转义显示，不是文件损坏。执行 `git config --global core.quotepath false` 可以让它正常显示中文名。

5. **每次提交都提示 `LF will be replaced by CRLF`。**
   Windows 和 Linux 的换行符不同，Git 在做自动转换。只是提醒，对网页和 PDF 没有影响。

6. **第一次把网站放在子文件夹里。**
   GitHub Pages 只能从仓库根目录或 `docs/` 发布，所以把 `index.html` 移到了根目录。

7. **左键点数字什么反应都没有（最难找的一个 bug）。**
   扫雷里"点已翻开的数字一次展开周围"是标准操作，但我一开始怎么点都没反应。AI 第一反应是判断"我没插旗，属于正常规则"——但我确实插了旗。
   后来重查代码才找到真因：左键点数字时确实调用了展开函数，却忘了调用界面刷新，所以数据变了、屏幕没重画。
   ai的修复办法是把所有玩家操作统一收进一个入口函数（执行 → 重画 → 计时 → 结算），从根上杜绝"漏掉重画"。另外加了一个界面层测试，专门盯这类问题。

8. **以为 Bestdori 的卡面图片地址是"照规律拼"就能用的。**
   我按印象里的路径规律拼了几个图片直链，请求时全部返回 200，看起来像是成功了。但一检查内容就发现不对：**返回的根本不是图片，而是同一个网页**——连我故意写错的文件名也返回 200。
   后来换了个思路：不去猜规律，而是去看**卡片数据本身**。卡片接口里有个 `resourceSetName` 字段，卡片 1 的值是 `res001001`（不是我以为的 `res0001`），真实地址就是 `资源目录名 + _rip/card_normal.png`。
   验证方式和前面一样——不看状态码，直接检查返回内容的文件头是不是 PNG。抽查 40 位角色各一张，40/40 全是真图片（422KB–837KB），卡面功能这才真正做出来。

9. **AI 的"最长连胜"永远停在 2。**
   因为我把 AI 演示写成了"连续通关 2 局就自动停下"，又在每次重新开始时把连胜清零——两个设定叠在一起，最长连胜就再也涨不上去了。
   改成：**连胜只有 AI 踩雷才中断**，中途按停再开始不清零；达到 2 局时只显示「✅ 已达标」，演示继续跑，连胜接着累积。

## 两处关键逻辑详解（防"纯粘贴"自查）

以下两段是 AI 生成代码里最关键的部分，也是我**能自己讲清楚**的：

### 1. 头像为什么不会被拉变形（`object-fit: cover`）

```css
.avatar {
  width: 110px;
  height: 110px;
  border-radius: 50%;
  object-fit: cover;
  object-position: center top;
}
```

头像框是 110x110 的正方形，而证件照原图是竖长的长方形，两者宽高比完全不同。**如果不写 `object-fit`，浏览器默认按 `fill` 处理，会把图片强行拉伸到正方形，脸会被压扁。** `cover` 的作用是：保持原图比例放大，直到完全铺满方框，多出来的部分裁掉。再用 `object-position: center top` 指定"裁的时候以上方中心为基准"，这样优先保住头顶和脸，而不是从正中间对称裁掉一半。`border-radius: 50%` 只是把方框的四个角切掉，让它变成圆。

### 2. 时间线不用图片、也不用多余标签（`border-left` + `::before`）

```css
.timeline > li {
  position: relative;
  border-left: 2px solid #e5e7eb;
  margin-left: 5px;
  padding: 0 0 18px 22px;
}
.timeline > li::before {
  content: "";
  position: absolute;
  left: -8px;
  top: 7px;
  width: 12px;
  height: 12px;
  border-radius: 50%;
  background: var(--accent);
}
```

每条履历是一个 `<li>`。给它一条左边框（`border-left`），这条竖线就出来了；`position: relative` 的作用是把它变成"定位基准"，让里面绝对定位的元素以它为准。`::before` 是"伪元素"——它可以**在不往 HTML 里增加任何标签的前提下，凭空造出一个可以设置样式的元素**，这里造的就是那个小圆点。`left: -8px` 把它往左挪 8px，正好压在那条 2px 的竖线上。最后一项把竖线设成透明（`border-left-color: transparent`），线就自然收尾，不会拖出去一截。

用伪元素的好处：否则我得在每条履历里手写一个 `<span class="dot"></span>`，HTML 会变啰嗦，以后调整结构还容易漏掉。

## Git 与命令行速查

### 分支和合并是什么
分支是从主线拉出来的一条独立开发线，可以在这条线上随便改代码而不影响主线；合并就是把分支上的改动并回主线。

### 命令行
| `cd` | change directory | 切换当前所在目录，例如 `cd C:\Users\zhengxy\Desktop\examine1` |
| `ls` | list | 列出当前目录下的文件和文件夹（Windows PowerShell 里 `dir` 是同义词） |
| `mkdir` | make directory | 新建文件夹，例如 `mkdir images` |

### Git 常用命令
| `git init` | 把当前文件夹变成 Git 仓库（生成隐藏的 `.git` 目录） |
| `git status` | 查看当前状态：哪些文件改了、哪些还没提交 |
| `git add .` | 把当前目录的所有改动放进暂存区（`.` 表示"当前目录"） |
| `git commit -m "说明"` | 把暂存区的内容存成一个版本快照 |
| `git log --oneline` | 查看历史提交记录 |
| `git push` | 把本地的提交上传到 GitHub |
| `git pull` | 把 GitHub 上的更新拉回本地 |
| `git branch` | 查看、创建分支 |
| `git remote -v` | 查看远程仓库地址 |

## 信息安全实践

### 为什么选择 MIT 协议（ai帮我选的）
本项目是一个学习性质的个人作品，希望任何人都能自由查看、学习和使用其中的代码，不需要额外询问我，也不限制用途。MIT 协议正好满足这一点：**它是最简短、最宽松的常见开源协议之一，允许别人使用、修改、分发甚至商用，唯一的要求是保留我的版权声明，并且作者不为使用后果负责**。相比之下，GPL 要求衍生作品也必须开源，对这样一个网页小项目来说约束过强，所以没有选它。
### 其他安全措施
- **开启 GitHub 两步验证（2FA）**：即使密码泄露，别人也无法登录我的账号。
- **使用 `.gitignore` 排除隐私文件**：高清证件照原图和获奖证书照片不上传到公开仓库。
- **不在公开页面留手机号**：个人主页只保留邮箱和 GitHub 账号。
- **给 Git 配置本地代理**：所在网络阻断了 GitHub 的 443 端口，通过 `git config --global http.proxy` 走本机代理完成推送；登录凭据由系统的凭据管理器加密保存，不必每次输入密码。
- **不把别人的美术素材放进自己的仓库**：扫雷的角色主题只引用角色名、官方配色和图片地址，卡面图片由使用者自己提供（粘贴地址或本地选择），不会把官方素材文件提交上来。MIT 协议只覆盖我自己写的代码，覆盖不了第三方的图片版权。

### 两条"AI 给过、但我查证后发现是错的"信息

#### 第一条：仓库地址根本没有被粘贴坏

AI 说我执行 `git push` 失败后，把终端输出发给 AI，它判断是我把仓库地址粘贴坏了——说地址前后混进了 Markdown 的方括号，变成 `[https://...](https://...)`，所以 Git 连不上，需要重新设置远程地址。
查证过程：我没有直接照着改，而是先执行 `git remote -v` 查看仓库里实际存的值。输出是：

```
origin  https://github.com/Kot0r11/examine1 (fetch)
origin  https://github.com/Kot0r11/examine1 (push)
```

结论：地址是干净的，根本没有方括号。那对括号是聊天窗口把网址自动渲染成超链接造成的显示效果，被 AI 误当成了真实内容。
真正的原因：梯子不知道为啥发癫了连不上，后面用校园网突然发现可以直连（话说校园网有时候可以连有时候又不可以） ai说是：网络层面阻断了 `github.com` 的 443 端口。逐个测试了连通性，`github.com:443` 超时不通，但 `github.com:22`（SSH）和本机代理是通的，所以改用代理才推送成功。
我的收获：不要相信"看起来像"的现象。判断问题要去看实际值——`git remote -v` 看真实地址、`git status` 看真实状态，而不是从报错的显示效果去猜。

#### 第二条：Bestdori 的卡面地址不能靠"规律"拼出来

AI 的说法：做角色主题时，AI 按社区常见的路径规律拼出了卡面图片地址，并用工具请求验证，返回的都是 200，于是判断"链接可用"。然后做出来没有什么作用
查证过程：我没有直接采信，而是检查返回的内容本身——用 Python 读了一下，发现这些 200 全都不是图片，而是同一个网页；AI 又故意请求了一个不存在的文件名，同样返回 200。
结论：那个站点对任何路径都返回网页外壳，200 完全不能证明链接有效。"请求成功"不等于"拿到了想要的东西"，必须检查返回内容。
后来的进展：AI 当时的结论是"这个站点的图片地址没法可靠获得"，于是退而求其次，改成让我自己提供图片。
但我又追问了一次，然后让他自己再bestdori里面找找，然后ai这次换了思路—卡片接口里有个 `resourceSetName` 字段，卡片 1 的值是 `res001001`，真实地址就是 `资源目录名 + _rip/card_normal.png`。按这个规律抽查 40 位角色，40/40 都是真图片，卡面选择功能这才真正做出来。

**我的收获**：
ai有时候骗人，得压力一下，通过连续追问逼问啥的才会往正确的方向想
